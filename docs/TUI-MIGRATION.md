# v1.3.0 development preview (T1-T4)

The Graphite Dark design uses #212121 background, #171717 sidebar, #292929 panels, #383838 borders, #ECECEC primary text and #A0A0A0 muted text. Semantic green, amber and red are restricted to status. Layout follows the approved sidebar and dashboard concept within terminal cell constraints. Minimum useful viewport is 42x10; sidebar collapses below 76 columns. Recommended terminal: Windows Terminal, 110x35 or larger, UTF-8, truecolor font with box drawing support.

Run Launch-TUI.cmd or bin/dcr-manager.exe. Build-TUI.cmd builds locally with Go. The executable currently expects the adjacent project src directory: it is not yet a standalone distribution. Keys: arrows or 1-9 select pages; Enter/Tab focuses scrolling, Esc returns to navigation; R refreshes; Q exits. Mouse clicks select sidebar items. PageUp/PageDown scroll. Diagnostics refresh asynchronously. --snapshot prints JSON; --render prints the actual dashboard at 110x35; --version prints 1.3.0-dev.

Architecture: cmd/dcr-manager is the entrypoint, internal/app holds typed contracts, internal/backend runs the existing read-only Windows PowerShell bridge with a timeout, internal/tui renders Bubble Tea/Lip Gloss and Bubbles viewport. All nine pages display real read-only diagnostics or fixed build metadata. Legacy Launch.cmd remains the supported mutation workflow. The Go executable does not yet perform start/stop, repairs, cache quarantine, backup restore, or config writes. No cloud-connectivity assertion.

T1 foundation, T2 theme, T3 shell and T4 dashboard are implemented as a development preview. Pending: native adapters, mutations with confirmation and regression parity, localization, settings persistence, independent distribution, visual comparison in a real interactive terminal, clean Windows VM tests, release review. Do not tag v1.3.0 until acceptance criteria are met; stable VERSION stays 1.2.1 during development.

## Visual stabilization before T5
All visible cells are painted explicitly with the Graphite Dark palette, including background gaps, borders, sidebar, header, footer and scroll viewport. Nested SGR resets restore the local surface. The frame uses exactly the terminal width and height. The sidebar collapses in narrow or short terminals; navigation focus appears in the footer. Package cards use human-readable labels and semantic status, and all diagnostic pages share the card styles. Windows diagnostic subprocesses use CREATE_NO_WINDOW to avoid attaching to the interactive console. Visual regression tests cover all nine pages at representative viewport sizes, explicit background coverage, exact palette and package labels. Render a particular page with --render --render-page 3. Interactive Windows Terminal visual acceptance remains pending.

## T5: Remote lifecycle controls (transitional backend)
Connection now has S Start, X Stop and T Restart. Stop/restart display a confirmation and default to no action unless Y is pressed; Esc/N cancels. Actions run in tea.Cmd; duplicate commands are blocked during an operation. An observed process snapshot is required; failed refresh disables actions. The Go adapter validates the action and expected Remote PID list, then invokes only the fixed Windows RemoteAction.ps1 bridge. The bridge shares the legacy manager mutex, rechecks the PID set and revalidates creation time and command line immediately before each targeted stop. Restart refuses to launch if stop is incomplete or the dedicated install is missing. Start verifies a local process appears within the bounded wait, not cloud connectivity. A refresh is requested on either success or error.

Tests: mocked actions, cancellation, duplicate start, async scheduling, failure refresh, small-screen confirmation and argument validation; a live mismatched-PID request was refused without stopping any process. No real start/stop/restart was run on the active Remote session. Native Go Windows process adapters and full lifecycle validation on an isolated session remain pending. As with the legacy CIM-based implementation, PID verification is not an atomic process handle; external clients can race. The current T5 is functional integration, not final native parity. Package/cache/recovery mutations remain in Launch.cmd.

## T5 native Windows lifecycle
The Go executable now uses golang.org/x/sys/windows (already a transitive dependency) for process discovery (Toolhelp32 + process command line query), creation FILETIME, retained handles, termination and a separate interactive Node console. No PowerShell action subprocess is used by the TUI. The prior action script remains as historical reference; legacy Launch.cmd remains available.

Native and legacy read-only inventories must agree before controls are enabled. The action contract carries PID + creation FILETIME. Recognized script paths are normalized, including npm .bin/../ paths. Only recognized absolute DCR script invocations and matching Remote descendants are eligible; ambiguous or inaccessible process inventories are not treated as permission to act. Preflight binds all target handles before any termination, verifies the set again, and waits for exit. A Windows mutex shared with the legacy manager serializes participating managers. Start creates a new console directly, bypasses npx and checks the launched process identity; restart preflights the dedicated install and refuses to start while a recognized Remote is still present. External software can still race or invoke unsupported layouts; the tool cannot guarantee atomicity across unrelated clients. Stop is forced termination, not graceful protocol shutdown.

Verified on this Windows host: independent inventory agreement, mismatched identity refusal, real handle preflight with intentionally invalid fixture targets, isolated start/stop/start/stop using a temporary inert Node script with DCR-shaped path, UI confirmation/cancellation, resize protection and regression tests. The fixture does not connect to Desktop Commander or use its credentials. Actual upstream Remote start/stop/reconnect and clean VM validation remain pending; the existing active session was not touched. Diagnostic and other maintenance operations still use the PowerShell bridge. Controls require a 50x14 terminal or larger to make confirmation visible. Stable version and main are unchanged.

## T6 package and cache management
Packages exposes P to repair the observed installed version (or install latest when absent) and U to explicitly update to latest. Cache exposes C to cycle eligible candidates and Z to quarantine the selected cache. Y confirms; N/Esc cancels. No operation runs automatically. Maintenance executes asynchronously, blocks competing controls, and refreshes diagnostics on completion. Visible confirmation requires a terminal of at least 50x14.

Go validates the fixed action, version or cache identity and invokes MaintenanceAction.ps1. PackageCache.psm1 reuses the tested legacy filesystem transaction and shared manager mutex. Package changes are refused while recognized DCR/MCP processes are active. Before switching, npm installs into a separate staging directory with its own cache; the staged package name, manifest, exact dependency, entry point and expected version are validated, active processes and the original version are checked again, and only package files are switched. Remote credentials are outside the switch. Previous files remain backed up; a failed switch attempts rollback and reports incomplete recovery. The stage and logs are retained for diagnosis. npm uses ordinary lifecycle scripts and network settings; its fetch timeout/retries are bounded, not the duration of all lifecycle scripts.

Cache discovery checks exclusive DCR dependencies, installed package identity, reparse-point safety and an opaque token derived from path, creation time, manifest hash and version. The selected candidate is rechecked before same-volume quarantine; active references are refused. Restore metadata is stored alongside the backup, with no global npm cache purge. Unknown or mixed cache layouts, stale tokens and ambiguous inventories are refused. A shared mutex coordinates participating managers; external software can still race. Errors use sanitized codes including EBUSY, EPERM and EACCES. No raw npm output is displayed in the TUI.

Verified: isolated fixture installation/repair/update, stage failure, late active-process guard, stale selection, actual Windows sharing-violation classification, selective quarantine and restore metadata; Go controls, request validation and prior regressions. Live read-only inventory and deliberate refusal cases were checked without touching the active installation or cache. No real npm download/swap of the installed DCR or live cache move has been performed in this stage. Package/cache operations still use PowerShell; native Go lifecycle from T5 is unchanged. Recovery and retention UI remain T7. Stable version and main remain unchanged.
